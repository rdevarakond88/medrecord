# Backend Deployment — What We Did and Why

_Written for a non-developer. No assumed technical knowledge._

---

## The Simple Version

The app on your phone needs a server to talk to. Without a server, the app can't log in, can't look up patients, can't save visits — it just fails silently or shows errors. Before we could test the app on a real device, we needed that server to exist and be reachable from the internet.

That's the only reason we did any of this.

---

## What Is the "Backend"?

Think of the app on your phone as the front of a shop — what the doctor sees and taps. The backend is the storage room and the brain behind it:

- It checks whether a doctor's OTP is correct
- It stores patient records in a database
- It decides whether a doctor is allowed to see another doctor's notes (consent rules)
- It keeps the audit log required by India's DPDP Act

The backend is a program that runs on a server somewhere on the internet, waiting for the app to send it requests and responding with data.

---

## Why Render?

The backend code was written and sitting in the GitHub repository, but it wasn't running anywhere. It was like a shop that was fully built but had no electricity and no address.

We needed a place to:
1. Run the backend code 24/7
2. Store the database (patient records, doctors, visits)
3. Give it a public internet address so your phone can reach it

**Render** (render.com) is a hosting service — think of it like renting space on a server. We chose it because:
- It has a free tier (no credit card needed to start)
- It connects directly to GitHub, so when code changes it redeploys automatically
- It provides a PostgreSQL database (the storage) for free

The URL we got: `https://medrecord-api.onrender.com`

## What Information Was Needed

| Item | What It Is | Where It Lives |
|---|---|---|
| GitHub repo access | So Render can read the code | Connected during Render signup |
| `DATABASE_URL` | The address of the database | Auto-set by Render (we didn't touch this) |
| `JWT_SECRET` | A secret key used to sign login tokens | Auto-generated by Render |
| `TEST_OTP_BYPASS=true` | Allows code `000000` instead of a real SMS OTP | Set in render.yaml by us |

No AWS credentials, no SMS provider, no credit card — kept to the minimum needed to get device testing unblocked.

## What I Tested (and What It Proves)

After deployment, I ran three checks using `curl` — a command-line tool that sends requests to a server, exactly like the app does, but without the phone screen in between.

### Check 1 — Health endpoint
```
GET /health → { "status": "ok" }
```
**What this proves:** The server is running and reachable from the internet. This is the device testing pre-flight check required by `AGENT_ORCHESTRATION.md` before any device test session can begin.

### Check 2 — Send OTP
```
POST /auth/send-otp (mobile: 9999999999) → { otp_token: "tok_..." }
```
**What this proves:** The server accepted the request, generated an OTP, stored it in the database, and returned a token. The database is working.

### Check 3 — Verify OTP
```
POST /auth/verify-otp (otp_token + otp: 000000) → { access_token, user: { name: "Dr. Test Doctor" } }
```
**What this proves:** The server found the test doctor in the database, validated the OTP, issued a JWT login token, and returned the doctor's profile. The full login flow works end-to-end at the server level.

## Is This the Same as Device Testing?

**No. These are two completely separate things.**

| | What I just did (API verification) | Device testing (what comes next) |
|---|---|---|
| **What runs** | curl commands from a terminal | The actual app on your iPhone |
| **What it tests** | Does the server respond correctly? | Does the full app work for a real doctor? |
| **What it can catch** | Server bugs, database errors, wrong response shapes | UI bugs, navigation bugs, offline behaviour, screen layout issues |
| **What it cannot catch** | Anything about the phone, the app code, the UI | Nothing about the server alone |
| **Who does it** | Me, in this session | You, on your phone, guided by the Device Tester agent |

Think of it this way:

> API verification = checking that the engine starts when you turn the key in the garage.
> Device testing = actually driving the car on the road.

Both are required. One without the other leaves gaps.
